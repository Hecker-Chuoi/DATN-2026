CI/CD cho hệ thống quản lý công việc trên một máy EC2

Mỗi lần đẩy code lên GitHub, Jenkins tự kiểm thử, đóng gói thành Docker image và cập nhật hệ thống đang chạy trên server; có lỗi thì tự quay về bản trước. Tài liệu này so sánh hai cách làm việc đó trên một máy EC2 duy nhất: chỉ dùng Docker, hoặc thêm Kubernetes (k3s).

Jenkins (Multibranch) Docker / Compose Kubernetes k3s HTTPS Let's Encrypt 1 × EC2 Ubuntu 24.04

01Bộ tài liệu gồm gì

Bạn đang ở trang Tổng quan. Trang này giải thích khái niệm, nêu những chỗ trong repo phải sửa trước khi deploy, so sánh hai hướng và chi phí. Mỗi hướng có trang riêng, đủ để làm theo từ đầu đến cuối.

Hướng 1

Docker thuần

Docker Compose + Caddy (HTTPS) + Jenkins. Ít thành phần, dễ hiểu, chạy được trên máy 8–16 GB.

 Hướng 2

Docker + Kubernetes (k3s)

k3s + Traefik Ingress + cert-manager + registry nội bộ. Rolling update không gián đoạn, tự phục hồi. Cần máy 16 GB.

02CI/CD là gì (giải thích từ con số 0)

Hiện tại muốn đưa bản mới lên server, ai đó phải: kéo code, build backend bằng Maven, build frontend bằng npm, build Docker image, SSH vào server, dừng container cũ, chạy container mới, rồi mở web kiểm tra. Làm tay thì chậm, dễ quên bước, và mỗi người làm một kiểu. CI/CD giao toàn bộ chuỗi việc đó cho máy, chạy giống hệt nhau mỗi lần.

CI · Continuous Integration

Tích hợp liên tục

Mỗi lần push hoặc mở Pull Request, máy tự build và chạy test. Code hỏng bị phát hiện trong vài phút, trước khi merge vào nhánh chính. Chạy cho mọi nhánh.

CD · Continuous Delivery

Chuyển giao liên tục

Mỗi bản qua CI đều được đóng gói thành image, sẵn sàng deploy. Việc đưa lên server chỉ còn một cú bấm (có bước người duyệt).

CD · Continuous Deployment

Triển khai liên tục

Bỏ luôn cú bấm: bản qua test được tự động đưa lên server. Tài liệu này dùng cách này cho nhánh main.

Service backend lấy khoá công khai (JWKS) của Keycloak qua mạng nội bộ http://keycloak:8080, nhưng kiểm tra claim iss theo URL công khai https://auth….

Bẫy số 1 khi lên server: issuer của JWT Token do Keycloak phát có claim iss (ví dụ https://auth.datn.example.com/realms/datn-realm). Gateway và các service so claim này với issuer-uri trong cấu hình; lệch một ký tự (http với https, có hay không có cổng) là mọi API trả 401. Trên máy dev, issuer là http://localhost:8088/.... Trên server, tài liệu cố định URL công khai của Keycloak bằng KC_HOSTNAME_URL=https://auth.... Nhờ vậy token có iss giống nhau dù identity-service gọi Keycloak qua mạng nội bộ. Stage smoke test của pipeline có một bước kiểm tra riêng điều này.

05So sánh 2 hướng

Hai hướng giống nhau ở phần CI: cùng Jenkins, cùng stage 1–4 (checkout, phát hiện thay đổi, test backend, lint/build frontend), cùng Dockerfile, cùng prod.env, cùng cách lưu bảng tag để rollback. Chúng chỉ khác ở phần CD, tức là ai chạy container và chạy bằng cách nào.

Hướng 1 · Docker thuần

Docker Compose đọc file YAML và giữ cho các container chạy đúng như mô tả. Jenkins đổi tag image trong deployed.env rồi gọi docker compose up -d. Compose chỉ tạo lại container nào có thay đổi. Caddy lo HTTPS.

Hướng 2 · Kubernetes (k3s)

k3s là Kubernetes rút gọn, liên tục so trạng thái thật với trạng thái mong muốn. Jenkins push image lên registry rồi kubectl apply. K8s cập nhật cuốn chiếu (bật Pod mới, đợi sẵn sàng rồi mới tắt Pod cũ). Traefik + cert-manager lo HTTPS.

06Nên chọn hướng nào? Lộ trình đề xuất

Khuyến nghị Làm Hướng 1 trước, sau đó nâng lên Hướng 2 nếu còn thời gian. Hướng 1 cho bạn một hệ thống chạy thật trên tên miền có HTTPS sau 1–2 ngày, đủ để demo và lấy phản hồi. Khoảng 70% công sức dùng lại được cho Hướng 2: image, Dockerfile, Jenkins, stage 1–4 của Jenkinsfile, prod.env, cấu hình Keycloak và tên miền. Khi nâng cấp, bạn chỉ thay phần "chạy container" (stage 5–7) và cài k3s.

  1. Tuần 1: Hướng 1 chạy được

    Sửa 14 điểm ở mục 4 (copy file common/), dựng EC2, Jenkins, Caddy, deploy lần đầu, cấu hình Keycloak và Google. Có link HTTPS để demo.

  2. Tuần 2: Ổn định

    Bật webhook, thử một vòng "push code → tự deploy", thử cố tình làm hỏng để xem rollback tự động, đặt lịch backup DB, đo RAM bằng docker stats.

  3. Tuần 3–4 (tuỳ chọn): Hướng 2

    Backup DB, gỡ stack Compose (Caddy và Traefik cùng cần cổng 80/443, không chạy song song được), cài k3s, áp manifest, khôi phục DB. Tài liệu Hướng 2 có mục chuyển đổi riêng.

Không nên Chạy cả hai hướng song song trên cùng một EC2. Cả hai cùng tranh cổng 80/443, tốn gấp đôi RAM, và hai bộ DB khác nhau sẽ lệch dữ liệu.

8.1 Tên miền & DNS

Cần tên miền thật vì Let's Encrypt không cấp chứng chỉ cho địa chỉ IP, và Google OAuth không chấp nhận redirect về IP. Có 2 lựa chọn:

  • Tên miền riêng (khuyên dùng): mua .com, .id.vn, .site… và quản lý DNS ở nhà cung cấp hoặc Cloudflare (để chế độ DNS only, tắt proxy màu cam để Let's Encrypt xác thực được).
  • DuckDNS (miễn phí): ví dụ datn2026.duckdns.org. Subdomain auth.datn2026.duckdns.org tự trỏ về cùng IP.

8.3 GitHub ↔ Jenkins

  1. Tạo Personal Access Token

    GitHub → Settings → Developer settings → Fine-grained tokens: chọn repo DATN-2026; quyền Contents: Read, Metadata: Read, Commit statuses: Read and write (để Jenkins báo ✓/✗ lên commit), Pull requests: Read.

  2. Lưu vào Jenkins

    Manage Jenkins → Credentials → System → Global → Add: Kind Username with password, Username = tên GitHub, Password = token, ID github-pat.

  3. Tạo Multibranch Pipeline

    New Item → Multibranch Pipeline → Branch Sources: GitHub, credential github-pat, URL repo. Build Configuration → by Jenkinsfile, Script Path = infrastructure/cicd/docker/Jenkinsfile (Hướng 1) hoặc infrastructure/cicd/k8s/Jenkinsfile (Hướng 2). Nếu muốn bỏ qua các nhánh cũ, thêm behaviour Filter by name, ví dụ main develop PR-*.

  4. Webhook

    GitHub repo → Settings → Webhooks → Add: Payload URL https://jenkins.<domain>/github-webhook/ (có dấu / cuối), Content type application/json, events: Pushes + Pull requests. Trong Jenkins: Manage Jenkins → System → Jenkins URL = https://jenkins.<domain>/.

Chiến lược nhánh main: CI + build image + deploy lên server. develop, nhánh tính năng, Pull Request: chỉ CI (test + lint + build), không đụng tới server. Quy trình của nhóm: làm ở nhánh tính năng → PR vào develop (CI phải xanh) → PR develop → main khi muốn phát hành. Muốn deploy từ develop thì đổi DEPLOY_BRANCH trong Jenkinsfile.

8.4 Cấu hình Keycloak & Google sau lần deploy đầu

Realm được import tự động từ infrastructure/keycloak/realm-export_08082026.json ở lần khởi động đầu, nhưng realm này chỉ biết các URL localhost. Sau lần deploy đầu tiên:

  1. Đăng nhập Admin Console

    https://auth.<domain>/admin, dùng KC_ADMIN_USER/KC_ADMIN_PASSWORD trong prod.env, rồi chọn realm datn-realm.

  2. Client datn-backend

    Clients → datn-backend → Settings: thêm Valid redirect URIs https://datn.<domain>/*, Web origins https://datn.<domain>. Có thể xoá các URI localhost.

  3. Tạo lại client secret

    Credentials → Regenerate (secret cũ đã nằm trên Git, coi như lộ). Copy secret mới vào KC_CLIENT_SECRET trong prod.env, cập nhật credential datn-prod-env trong Jenkins, rồi chạy lại pipeline với BUILD_ALL=true để identity-service nhận secret mới.

  4. Google SSO

    Identity providers → google: copy Redirect URI (dạng https://auth.<domain>/realms/datn-realm/broker/google/endpoint). Google Cloud Console → APIs & Services → Credentials → OAuth client: thêm URI đó vào Authorized redirect URIs và https://datn.<domain> vào Authorized JavaScript origins.

  5. Tài khoản admin ứng dụng

    Tạo user có realm role ADMIN (Users → Add user → Role mapping), hoặc đăng ký trên web rồi gán role.

Lưu ý về realm import Keycloak chỉ import realm khi realm chưa tồn tại. Mọi chỉnh sửa trong Admin Console được lưu trong keycloak-db, deploy lại không ghi đè. Nếu muốn đưa cấu hình mới về Git thì export lại realm (Realm settings → Action → Partial export).

# =============================================================================
# Dockerfile "runtime-only" dùng chung cho MỌI service Spring Boot trong pipeline.
# Đặt trong repo tại: backend/Dockerfile.runtime
#
# Ý tưởng "build once": Jenkins đã chạy `mvn package` (test + đóng gói jar) MỘT lần
# cho cả reactor. Image chỉ việc chép file jar có sẵn vào JRE → nhanh, ít RAM,
# không phải compile lại 5 lần trong 5 Dockerfile multi-stage.
#
# Build context = thư mục target của service, ví dụ:
#   docker build -f backend/Dockerfile.runtime -t datn/work-service:15-a1b2c3d backend/work-service/target
# (trong target chỉ có 1 file *.jar; file *.jar.original không khớp glob)
#
# Các Dockerfile multi-stage cũ trong từng service vẫn giữ nguyên cho docker-compose local.
# =============================================================================
FROM eclipse-temurin:21-jre-alpine

# Không chạy bằng root
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app
COPY *.jar app.jar
USER app

# Heap tự co giãn theo giới hạn RAM của container (mem_limit trong compose / limits trong k8s).
# SerialGC: ít tốn RAM nhất cho heap nhỏ (< 1GB). ExitOnOutOfMemoryError: chết hẳn để Docker/K8s khởi động lại.
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70 -XX:+UseSerialGC -XX:+ExitOnOutOfMemoryError"

ENTRYPOINT ["java", "-jar", "/app/app.jar"]

# =============================================================================
# frontend/nginx.prod.conf – Nginx của container frontend khi chạy PRODUCTION
#
# Container frontend CHỈ phục vụ file tĩnh (SPA). Việc chia đường dẫn API
# (/identity, /work, /workspace → api-gateway) do lớp biên đảm nhận:
#   - Hướng 1: Caddy   - Hướng 2: Traefik Ingress của k3s
#
# Vì sao không proxy API ở đây như nginx.conf cũ?
#   Nginx phân giải tên "api-gateway" ra IP MỘT lần lúc khởi động rồi nhớ mãi.
#   Khi Jenkins deploy lại gateway (container mới → IP mới) nginx vẫn gọi IP cũ → 502.
#   Caddy/Traefik phân giải lại theo từng kết nối nên không bị lỗi này.
# =============================================================================
server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    gzip on;
    gzip_min_length 1024;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;

    # File build của Vite có hash trong tên (index-AbC123.js) → cache lâu dài được
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    # index.html KHÔNG cache để người dùng luôn nhận bản mới sau mỗi lần deploy
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # React Router: mọi đường dẫn lạ đều trả về index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}

Đề xuất thêm: actuator cho mọi service

Để health check kiểm tra được "app thực sự hoạt động, kết nối được DB" chứ không chỉ "cổng đã mở", nên thêm vào pom.xml của identity, work, workspace, notification:

xmlpom.xml (mỗi service)
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

rồi cho phép truy cập không cần token trong SecurityConfig của từng service: .requestMatchers("/actuator/health/**").permitAll(). Sau đó đổi healthcheck/probe từ TCP sang /actuator/health/readiness và /actuator/health/liveness (Spring Boot tự bật hai nhóm này khi chạy trong Kubernetes).
