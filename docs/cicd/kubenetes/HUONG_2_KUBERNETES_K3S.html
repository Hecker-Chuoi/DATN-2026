Ba câu hỏi "vì sao" quan trọng

Vì sao Jenkins ở NGOÀI k3s?

(1) Tránh vòng luẩn quẩn: cluster hỏng thì vẫn còn Jenkins để sửa. (2) Build image trong Pod phải dùng Kaniko hoặc BuildKit, phức tạp hơn nhiều so với dùng docker.sock. (3) Dùng lại y nguyên image Jenkins của Hướng 1.

Vì sao phải có registry?

k3s dùng containerd riêng, không nhìn thấy kho image của Docker. Image Docker vừa build phải được push lên localhost:5000 rồi k3s mới pull về được. Registry chỉ nghe ở 127.0.0.1, không lộ ra ngoài.

Jenkins có HTTPS bằng cách nào?

Traefik đã chiếm 80/443 nên không dùng Caddy được. Ta tạo một Service không có selector, kèm Endpoints trỏ <private-ip>:8080, rồi gắn Ingress lên. Traefik coi Jenkins như một service trong cluster (file bootstrap/jenkins-ingress.yaml).

06Deploy khai báo & rolling update

6.1 Từ bảng tag đến manifest cuối cùng

Trong manifests/apps/*.yaml, image chỉ ghi tên (image: datn/work-service), không có tag. Mỗi lần deploy, Jenkins đọc /opt/datn/state/deployed.env (cùng cơ chế với Hướng 1) và sinh một overlay nhỏ:

yaml.k8s-overlay/kustomization.yaml (Jenkins tự sinh, không commit)
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../infrastructure/cicd/k8s/manifests      # manifest gốc trong repo
images:                                       # ↓ đọc từ deployed.env
  - name: datn/work-service
    newName: localhost:5000/datn/work-service
    newTag: "57-a1b2c3d"
  - name: datn/identity-service
    newName: localhost:5000/datn/identity-service
    newTag: "41-9f8e7d6"
  # ... 4 service còn lại

kubectl kustomize thay image: datn/work-service bằng localhost:5000/datn/work-service:57-a1b2c3d rồi kubectl apply nộp toàn bộ. API server so với trạng thái đang chạy: chỉ Deployment work-service có pod template đổi nên chỉ nó được rolling update. 11 workload còn lại báo unchanged, Pod không bị động tới.

Vì sao không dùng kubectl set image? set image là lệnh mệnh lệnh: nó sửa trực tiếp trên cluster nhưng không ghi lại ở đâu. Lần sau ai đó kubectl apply manifest gốc thì image sẽ bị đổi về giá trị trong file (gọi là "drift"). Với overlay sinh từ bảng tag, một nguồn sự thật (Git + deployed.env) luôn tạo ra đúng một trạng thái cluster.

6.2 Rolling update không gián đoạn

Mỗi Deployment ứng dụng có maxSurge: 1, maxUnavailable: 0. Ví dụ khi đổi work-service từ v56 lên v57:

t0 · apply
v56 · Ready · nhận traffic
t1 · surge
v56 · Ready · nhận trafficv57 · đang khởi động (startupProbe)
t2 · ready
v56 · Readyv57 · Ready → Service thêm vào
t3 · thay
v56 · Terminatingv57 · Ready · nhận traffic
Nếu v57 lỗi
v56 vẫn phục vụv57 CrashLoop / không Ready→ rollout status hết giờ → Jenkins rollback

Người dùng không gặp lỗi nào trong suốt quá trình, vì Service chỉ gửi request tới Pod đã Ready. Đây là khác biệt lớn nhất so với Hướng 1 và là phần đáng trình diễn khi bảo vệ (cách làm ở mục 10, bước 12).

Chi phí của zero-downtime Trong lúc cập nhật, cả Pod cũ và Pod mới cùng chạy, nên RAM tăng tạm thời bằng một Pod (tối đa ~1 GB với work-service). Keycloak và các DB dùng Recreate / StatefulSet một bản nên vẫn gián đoạn ngắn khi chính chúng được nâng cấp. Việc này hiếm khi xảy ra vì chúng không đổi theo code.

07Đọc hiểu manifest

7.1 Giải phẫu một Deployment

yamlapps/work-service.yaml (rút gọn, có chú thích)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: work-service
spec:
  replicas: 1
  revisionHistoryLimit: 5              # giữ 5 ReplicaSet cũ → `kubectl rollout undo`
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # zero-downtime
  selector:
    matchLabels: { app: work-service } # Deployment quản lý Pod có nhãn này
  template:                            # "khuôn" Pod – đổi bất cứ gì ở đây = rolling update
    metadata:
      labels: { app: work-service, tier: app }
    spec:
      enableServiceLinks: false        # không bơm biến *_PORT=tcp://... vào Pod
      containers:
        - name: app
          image: datn/work-service     # Kustomize gắn registry + tag
          envFrom:
            - configMapRef: { name: datn-config }        # URL nội bộ, Redis, Kafka, MinIO...
          env:
            - name: AUTH_DOMAIN
              valueFrom: { secretKeyRef: { name: datn-secrets, key: AUTH_DOMAIN } }
            - name: SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUERURI
              value: "https://$(AUTH_DOMAIN)/realms/datn-realm"   # K8s tự ghép biến khai báo phía trên
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom: { secretKeyRef: { name: datn-secrets, key: APP_DB_PASSWORD } }
          startupProbe:  { tcpSocket: { port: 8083 }, periodSeconds: 5, failureThreshold: 60 }  # ≤ 5 phút để boot
          readinessProbe: { tcpSocket: { port: 8083 }, periodSeconds: 10 }   # Ready mới nhận traffic
          livenessProbe:  { tcpSocket: { port: 8083 }, periodSeconds: 20 }   # treo → restart
          resources:
            requests: { cpu: 150m, memory: 512Mi }   # "giữ chỗ" khi xếp lịch
            limits:   { memory: 1Gi }                # vượt → OOMKilled → tự khởi động lại

7.2 Ba loại probe & vì sao cần startupProbe

ProbeCâu hỏiKhi thất bại
startupProbe"Đã khởi động xong chưa?"Chờ tiếp, tới failureThreshold × periodSeconds thì restart. Trong lúc này hai probe kia chưa chạy
readinessProbe"Nhận request được chưa?"Bị gỡ khỏi Service (không nhận traffic), không restart
livenessProbe"Còn sống không hay đã treo?"Restart container

Spring Boot mất 30–90 giây để khởi động (work-service có Flyway và seed template). Nếu không có startupProbe, livenessProbe có thể giết Pod trước khi nó kịp boot xong, gây vòng lặp CrashLoop vô tận.

7.3 StatefulSet + PVC cho dữ liệu

Postgres, Redis, Kafka, MinIO dùng StatefulSet có volumeClaimTemplates. k3s tự tạo PVC (ví dụ data-app-db-0) bằng StorageClass local-path, tức là một thư mục trên ổ EBS của EC2. Xoá Pod hay deploy lại thì dữ liệu vẫn còn. Xoá PVC hoặc namespace thì mất dữ liệu, nên đừng chạy kubectl delete namespace datn khi chưa backup.

7.4 Bí mật & cấu hình

  • ConfigMap datn-config (trong Git): URL nội bộ (http://keycloak:8080, redis, kafka:9092…), profile prod, tuỳ chọn JVM. Mọi service Spring nạp toàn bộ bằng envFrom; key không dùng tới thì Spring bỏ qua.
  • Secret datn-secrets (không có trong Git): Jenkins tạo từ credential datn-prod-env, tức là cùng file prod.env với Hướng 1. Mỗi Pod chỉ lấy đúng key nó cần qua secretKeyRef.
  • $(AUTH_DOMAIN) trong value: được Kubernetes thay bằng biến môi trường khai báo phía trên trong cùng container. Nhờ vậy tên miền chỉ nằm ở prod.env, không phải viết cứng vào manifest (trừ ingress.yaml).
Bẫy: service links bơm biến lạ vào Pod Mặc định K8s bơm vào mỗi Pod các biến như KAFKA_PORT=tcp://10.43.12.7:9092 cho mọi Service trong namespace. Image apache/kafka biến mọi biến KAFKA_* thành cấu hình broker, nên nhận nhầm port=tcp://… và không khởi động được. Tất cả manifest đã đặt enableServiceLinks: false để tránh lỗi này (ứng dụng tìm nhau qua DNS, không cần các biến đó).

7.5 Ingress & HTTPS

ingress.yaml có hai host. datn.<domain> chia /identity, /work, /workspace → api-gateway:8081, còn lại → frontend:80. auth.<domain> → keycloak:8080. pathType: Prefix so khớp theo từng đoạn đường dẫn, nên /work không ăn nhầm /workspace. Annotation cert-manager.io/cluster-issuer: letsencrypt-prod khiến cert-manager tự tạo Certificate, giải thử thách HTTP-01 qua Traefik, rồi lưu chứng chỉ vào Secret datn-tls và tự gia hạn trước 30 ngày.

14Ưu / nhược điểm

Ưu điểm
  • Không gián đoạn khi deploy service ứng dụng (rolling update + readiness).
  • Tự phục hồi cả khi Pod chết lẫn khi Pod treo (liveness), tự giữ đủ số bản.
  • Hạ tầng mô tả hoàn toàn bằng code (manifest trong Git); k8s-rendered.yaml lưu vết từng lần deploy.
  • Scale một service bằng replicas, Service tự cân bằng tải.
  • Kỹ năng K8s dùng được ở doanh nghiệp; manifest chuyển sang EKS/GKE dễ dàng.
  • Phần trình diễn khi bảo vệ rất thuyết phục.
Nhược điểm
  • Nhiều khái niệm, đường học dốc; debug phải đi qua nhiều lớp.
  • Tốn thêm ~1–1,5 GB RAM cho phần nền; bắt buộc máy 16 GB.
  • Thêm thành phần phải bảo trì: registry (dọn tag), cert-manager, Traefik.
  • Vẫn chỉ 1 node: máy EC2 chết thì toàn hệ thống chết, K8s không cứu được.
  • DB chạy trong K8s với ổ local-path: ổn cho ĐATN, còn production thật thường dùng RDS.

// =============================================================================
// Jenkinsfile – HƯỚNG 2: Docker + Kubernetes (k3s) trên 1 EC2
// Đặt trong repo tại: infrastructure/cicd/k8s/Jenkinsfile
// Jenkins: Multibranch Pipeline → Build Configuration → Script Path = infrastructure/cicd/k8s/Jenkinsfile
//
// Luồng:
//   1 Checkout → 2 Phát hiện thay đổi → 3 CI backend → 4 CI frontend
//   → (chỉ nhánh main) 5 Build + push image lên registry localhost:5000
//   → 6 Deploy: sinh overlay kustomize từ deployed.env rồi `kubectl apply` (khai báo)
//   → 7 Chờ rollout + smoke test → lỗi thì TỰ ĐỘNG ROLLBACK.
//
// Credential cần có trong Jenkins:
//   - datn-prod-env  : Secret file (docs/cicd/common/prod.env.example)
//   - k3s-kubeconfig : Secret file (/opt/datn/kubeconfig-jenkins.yaml do setup-k3s.sh sinh ra)
// =============================================================================
import groovy.transform.Field

@Field List<String> BACKEND_SERVICES = ['identity-service', 'api-gateway', 'work-service', 'workspace-service', 'notification-service']
@Field List<String> ALL_TAG_KEYS = ['IDENTITY_SERVICE_TAG', 'API_GATEWAY_TAG', 'WORK_SERVICE_TAG',
                                    'WORKSPACE_SERVICE_TAG', 'NOTIFICATION_SERVICE_TAG', 'FRONTEND_TAG']

String tagKey(String svc) {
  return svc.toUpperCase().replace('-', '_') + '_TAG'
}

void addOnce(List<String> list, String item) {
  if (!list.contains(item)) { list.add(item) }
}

// Sinh overlay kustomize = manifest gốc + bảng tag hiện tại, rồi áp vào cluster.
// Kubernetes so sánh với trạng thái đang chạy và CHỈ rolling update Deployment nào có image đổi.
void renderAndApply() {
  sh(script: '''
    set -eu
    for k in ''' + ALL_TAG_KEYS.join(' ') + '''; do
      grep -q "^$k=" "$STATE_DIR/deployed.env" || { echo "Thiếu $k trong deployed.env → chạy lại với BUILD_ALL=true"; exit 1; }
    done

    rm -rf .k8s-overlay && mkdir -p .k8s-overlay
    {
      echo "apiVersion: kustomize.config.k8s.io/v1beta1"
      echo "kind: Kustomization"
      echo "resources:"
      echo "  - ../$CICD_DIR/manifests"
      echo "images:"
      grep -E '^[A-Z_]+_TAG=' "$STATE_DIR/deployed.env" | while IFS='=' read -r key tag; do
        svc=$(echo "$key" | sed 's/_TAG$//' | tr 'A-Z_' 'a-z-')
        echo "  - name: datn/$svc"
        echo "    newName: $REGISTRY/datn/$svc"
        echo "    newTag: \\"$tag\\""
      done
    } > .k8s-overlay/kustomization.yaml
    echo "----- overlay -----"; cat .k8s-overlay/kustomization.yaml

    kubectl kustomize .k8s-overlay > k8s-rendered.yaml       # manifest cuối cùng (lưu lại làm bằng chứng)
    kubectl apply -f k8s-rendered.yaml
  ''')
}

pipeline {
  agent any

  options {
    skipDefaultCheckout(true)
    timestamps()
    disableConcurrentBuilds()
    buildDiscarder(logRotator(numToKeepStr: '30'))
    timeout(time: 50, unit: 'MINUTES')
  }

  parameters {
    booleanParam(name: 'BUILD_ALL', defaultValue: false,
      description: 'Bỏ qua phát hiện thay đổi: build + deploy TẤT CẢ service (lần đầu / sau rollback)')
    string(name: 'ROLLBACK_TO', defaultValue: '',
      description: 'Số build muốn quay về (vd 42). Để trống = chạy bình thường')
  }

  environment {
    APP_DOMAIN    = 'datn.example.com'          // ĐỔI
    AUTH_DOMAIN   = 'auth.datn.example.com'     // ĐỔI
    DEPLOY_BRANCH = 'main'
    CICD_DIR      = 'infrastructure/cicd/k8s'
    STATE_DIR     = '/opt/datn/state'
    REGISTRY      = 'localhost:5000'
    NAMESPACE     = 'datn'
    MAVEN_OPTS    = '-Xmx1g'
  }

  stages {

    stage('1. Checkout') {
      steps {
        script {
          def scmVars = checkout scm
          env.PREV_OK_COMMIT   = scmVars.GIT_PREVIOUS_SUCCESSFUL_COMMIT ?: ''
          env.GIT_SHORT        = sh(returnStdout: true, script: 'git rev-parse --short=7 HEAD').trim()
          env.TAG              = "${env.BUILD_NUMBER}-${env.GIT_SHORT}"
          env.IS_DEPLOY_BRANCH = (env.BRANCH_NAME == env.DEPLOY_BRANCH) ? 'true' : 'false'
          env.MODE             = params.ROLLBACK_TO?.trim() ? 'rollback' : 'build'
          if (env.MODE == 'rollback') {
            if (env.IS_DEPLOY_BRANCH != 'true') { error("Chỉ rollback trên nhánh ${env.DEPLOY_BRANCH}") }
            if (!params.ROLLBACK_TO.trim().matches(/\d+/)) { error('ROLLBACK_TO phải là số build') }
          }
          echo "Nhánh=${env.BRANCH_NAME} | TAG=${env.TAG} | Chế độ=${env.MODE}"
        }
      }
    }

    stage('2. Phát hiện thay đổi') {
      when { environment name: 'MODE', value: 'build' }
      steps {
        script {
          List<String> files = null
          if (!params.BUILD_ALL && env.PREV_OK_COMMIT) {
            int rc = sh(returnStatus: true, script: "git diff --name-only ${env.PREV_OK_COMMIT} HEAD > .changed-files")
            if (rc == 0) {
              files = []
              for (String line : readFile('.changed-files').split('\n')) {
                if (line.trim()) { files.add(line.trim()) }
              }
            }
          }

          List<String> selected = []
          boolean infra = false
          if (files == null) {
            selected.addAll(BACKEND_SERVICES)
            selected.add('frontend')
            infra = true
          } else {
            for (String f : files) {
              if (f.startsWith('backend/common/') || f == 'backend/pom.xml' || f == 'backend/Dockerfile.runtime') {
                for (String s : BACKEND_SERVICES) { addOnce(selected, s) }
              }
              for (String s : BACKEND_SERVICES) {
                if (f.startsWith("backend/${s}/".toString())) { addOnce(selected, s) }
              }
              if (f.startsWith('frontend/')) { addOnce(selected, 'frontend') }
              // Sửa manifest k8s hoặc realm → cần apply lại dù không có image mới
              if (f.startsWith("${env.CICD_DIR}/".toString()) || f.startsWith('infrastructure/keycloak/')) { infra = true }
            }
            echo "Có ${files.size()} file thay đổi:\n" + files.join('\n')
          }

          boolean backendChanged = false
          for (String s : selected) { if (s != 'frontend') { backendChanged = true } }

          env.SERVICES         = selected.join(' ')
          env.HAS_SERVICES     = selected ? 'true' : 'false'
          env.BACKEND_CHANGED  = backendChanged ? 'true' : 'false'
          env.FRONTEND_CHANGED = selected.contains('frontend') ? 'true' : 'false'
          env.INFRA_CHANGED    = infra ? 'true' : 'false'
          echo "Service cần build: [${env.SERVICES}] | Manifest/realm đổi: ${env.INFRA_CHANGED}"
        }
      }
    }

    stage('3. CI · Backend: unit test + đóng gói jar') {
      when { allOf { environment name: 'MODE', value: 'build'; environment name: 'BACKEND_CHANGED', value: 'true' } }
      steps {
        dir('backend') { sh 'mvn -B -ntp clean package' }
      }
      post {
        always { junit allowEmptyResults: true, testResults: 'backend/**/target/surefire-reports/*.xml' }
      }
    }

    stage('4. CI · Frontend: lint + build') {
      when { allOf { environment name: 'MODE', value: 'build'; environment name: 'FRONTEND_CHANGED', value: 'true' } }
      steps {
        dir('frontend') {
          sh 'npm ci --no-audit --no-fund'
          sh 'npm run lint'
          sh 'npm run build'
        }
      }
    }

    stage('5. Build + push image lên registry') {
      when {
        allOf {
          environment name: 'MODE', value: 'build'
          environment name: 'IS_DEPLOY_BRANCH', value: 'true'
          environment name: 'HAS_SERVICES', value: 'true'
        }
      }
      steps {
        script {
          for (String s : env.SERVICES.split(' ')) {
            String image = "${env.REGISTRY}/datn/${s}:${env.TAG}"
            if (s == 'frontend') {
              sh """
                docker build -t ${image} \\
                  --build-arg VITE_KEYCLOAK_URL=https://${env.AUTH_DOMAIN} \\
                  --build-arg NGINX_CONF=nginx.prod.conf \\
                  frontend
              """
            } else {
              sh "docker build -f backend/Dockerfile.runtime -t ${image} backend/${s}/target"
            }
            // Khác Hướng 1: k3s (containerd) không thấy image của Docker → phải đẩy qua registry
            sh "docker push ${image}"
          }
        }
      }
    }

    stage('6. Deploy (kubectl apply)') {
      when {
        allOf {
          environment name: 'IS_DEPLOY_BRANCH', value: 'true'
          anyOf {

# =============================================================================
# registry-cleanup.sh – HƯỚNG 2: dọn registry localhost:5000
# Giữ các tag xuất hiện trong 5 lần deploy thành công gần nhất (+ bảng tag hiện tại),
# xoá các tag còn lại rồi chạy garbage-collect để giải phóng ổ đĩa.

STATE=/opt/datn/state
ACCEPT='Accept: application/vnd.docker.distribution.manifest.v2+json, application/vnd.oci.image.manifest.v1+json, application/vnd.oci.image.index.v1+json'

        | cut -d= -f2 | sort -u )
echo "Giữ lại các tag:"; echo "$KEEP"

  for tag in $(curl -fsS "$REG/v2/$repo/tags/list" | jq -r '.tags[]?'); do
